# Delta Lake 版本可恢复性分析网页

对象存储误删文件后，湖仓值班员用本工具查清一张 Delta Lake 表还有哪些
版本可以完整回退。值班员在网页上填写版本区间，上传三类材料：

1. `_delta_log` 中留存的 **JSON 提交**（`NNN.json`，20 位补零版本号）；
2. 留存的**经典单文件 Parquet 检查点**（`NNN.checkpoint.parquet`，用 PyArrow 读取）；
3. **现存数据文件的表内相对路径清单**（每行一个路径，如 `data/part-00000-….parquet`）。
   清单可以声明为**原样路径**或**URI 编码**，旧清单也可以不注明格式。

工具逐版从 **版本 0 的提交**或**不晚于该版的最新检查点**出发，连续重放
`add` / `remove` 动作到目标版本，再把重建出的快照引用文件与现存清单核对：

- 🟢 **可重建 · 文件齐全**：重放连续无断档，且快照引用的数据文件全部确认现存；
- 🔴 **缺失提交，重放中断**：明确给出缺失的提交号（版本号列表）；
- 🟠 **重放完整但缺数据文件**：明确给出每个缺失的数据文件表内相对路径；
- 🔵 **文件待确认，暂不可回退**：重放完整，但未注明格式的清单行既可读作
  原样路径、也可读作解码后路径，两种解释指向不同文件，需人工确认。

## 路径编码规则（重要）

Delta 的 JSON 提交与经典单文件 Parquet 检查点里的路径都是 URI 编码的，
本工具**只解码一次**：`%2520` → 字面 `%20`，`%20` → 空格。文件名里本来
就有 `%20` 时，日志中显示为 `%2520`，不会被误当成空格。

清单侧每份文件可选三种模式：

| 模式 | 声明方式 | 行为 |
|---|---|---|
| 原样路径 `raw` | 表单选择、`manifest_format_N=raw`、清单首行 `# format: raw`，或文件名含 `.raw.` | 逐行按字面保留，`%20` 就是文件名的一部分 |
| URI 编码 `uri` | 同上写 `uri`，或文件名含 `.uri.` | 每行只解码一次，`%20` → 空格、`%2520` → 字面 `%20` |
| 未注明 `auto` | 旧清单不写任何格式 | 原样与解码结果相同即算现存；指向不同路径时两条路径都记为待确认 |

- **有明确条目证实存在的文件仍算现存**：其他清单里的 raw/uri 条目或同路径
  的明确条目会覆盖待确认状态。
- 逐版分别列出**缺失**与**待确认**的引用文件；只有重放完整、且所有引用
  文件都确认现存，才标为可回退。存在明确缺失文件时优先报缺失文件。

**仅处理无删除向量（Deletion Vector）的表**：协议特性或任何 add/remove
动作中出现 `deletionVector` 时直接拒绝分析，并指出来源文件。

## 目录结构

```
app/
  analyzer.py            # 核心逻辑：日志解析、逐版重放、文件核对、DV 拦截
  web.py                 # Flask 路由：上传分析 + 本地样例 API
  templates/index.html   # 单页界面（服务端渲染与 JS 渲染共用）
scripts/generate_samples.py  # 用 PyArrow 构造样例 Delta 表
samples/                 # 本地样例（健康表 / 事故表 / 编码核对表 / 旧清单表）
tests/                   # pytest：核心逻辑与路由测试
Dockerfile / docker-compose.yml
```

页面下半部有四个按钮可**直接加载本地样例**，无需手动选择文件：

- **健康表样例（v0–v4）**：含 v2 检查点，5 个版本全部可重建；
- **误删事故样例（v0–v5）**：v3 提交丢失、数据文件 `part-00004` /
  `part-00006` 被删，但 v2/v4 检查点留存。预期结论：

  | 版本 | 结论 | 说明 |
  |---|---|---|
  | v0–v2 | 🟢 可重建 | v2 起以 `checkpoint-2` 为基线 |
  | v3 | 🔴 缺提交 | 缺提交号 v3 |
  | v4 | 🟠 缺数据文件 | 缺 `data/part-00004-incident.parquet`（v4 检查点仍引用它） |
  | v5 | 🟠 缺数据文件 | 缺 `part-00004` 与 `part-00006` |

  目录中还放了一个分片检查点残片，工具会明确列为“已忽略：仅支持经典
  单文件检查点”。

- **编码核对样例（v0–v2）**：同时上传对象存储导出的原样清单
  （`object_store_export.raw.txt`）与 URI 编码的备份清单
  （`backup_manifest.uri.txt`）。表中三个文件分别演示：

  | 文件名 | 日志中 | 原样清单 | URI 清单 | 结论 |
  |---|---|---|---|---|
  | `part-00000-literal%20name.parquet` | `%2520` | 字面 `%20` ✓ | 解码一次 → 字面 `%20` ✓ | 现存 |
  | `part-00001-space name.parquet` | `%20` | 空格 ✓ | 解码一次 → 空格 ✓ | 现存 |
  | `part-00002-literal name.parquet` | `%20` | 不在清单 | 不在清单 | **缺失**（旧逻辑会因字面 `%20` 同名文件误判为可回退） |

  v0、v1 为 🟢 可重建；v2 为 🟠 缺数据文件，缺 `part-00002-literal name.parquet`。

- **旧清单样例（v0–v1）**：清单未注明格式，条目
  `part-00000-literal%20name.parquet` 既可能指字面 `%20`、也可能指空格文件，
  两条路径都标为待确认；每版结论为 🔵 待确认（重放完整，但不可回退）。

## 手工上传分析

1. 填写“起始版本 / 结束版本”；
2. 多选上传 `_delta_log` 里留存的 `.json` 与 `.checkpoint.parquet`
   （文件名必须保持 20 位补零版本号，上传时带不带目录前缀都可以）；
3. 上传现存数据文件清单，并在“清单路径格式”选择原样路径 / URI 编码 /
   未注明；多份清单格式不同时，可按上传顺序填写 `manifest_format_0`、
   `manifest_format_1`…（或提交 `manifest_formats` JSON 数组），也可在清单
   首行写 `# format: raw|uri`，或用文件名提示（如 `export.raw.txt`）；
   支持 `#` 注释、空行、`./` 前缀；不上传清单则所有引用文件都判为缺失；
4. 提交后得到总览统计、输入材料盘点和逐版核对明细（可展开查看每个
   引用文件的 ✓ 已确认现存 / ? 待确认 / ✗ 缺失状态及清单证据）。

也可以只上传检查点：对不晚于检查点版本的目标版本，直接以检查点中的
add 列为快照基线；目标版本更新时，则从检查点版本 +1 起连续重放提交，
中途缺任一提交即报缺失提交号。检查点里的 remove 是墓碑，不属于快照。

## 设计取舍

- **基线选择**：优先使用不晚于目标版本的最新检查点（重放距离最短），
  无检查点时才要求版本 0 的提交；
- **逐版独立重放**：每个目标版本都从基线完整重放一次，缺提交不会污染
  其他版本的结论，报告中的“重放起点”对每版透明；
- **只认经典单文件检查点**：分片检查点（`N.checkpoint.K.M.parquet`）
  与 `_last_checkpoint` 指针不参与重放，只在页面登记忽略原因；
- **DV 硬拦截**：删除向量会让“文件存在 ≠ 行数据完整”，超出本工具
  基于文件清单的核对能力，因此在协议层和动作层双重检测并拒绝；
- **编码只解码一次**：日志 / 检查点固定按 URI 规范解码一次，清单侧由上传
  方声明原样还是 URI 编码，避免把文件名里的字面 `%20` 当成空格而误判
  可回退；未注明格式的旧清单不做猜测，歧义条目逐条列为待确认；
- **待确认不阻塞其他版本**：每版独立重放、独立核对，待确认只影响当前
  版本的可回退结论，已明确存在的文件仍计入现存。
